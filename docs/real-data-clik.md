# CLIK 지방의정포털 회의록 첫 실호출 (2026-09-28)

> 수치는 모두 이 세션에서 직접 본 것이고, 계산으로 낸 값은 "(계산)"으로 표시합니다.

국회도서관 지방의정포털(CLIK) Open API 키가 승인되어, 명세만 보고 작성했던 `sources/clik.py`로 처음 실제 호출을 했습니다.

- 키는 `APP_CLIK_API_KEY` 환경 변수로만 넘기고 `test -n`으로만 확인했습니다. 출력·파일·커밋에 남기지 않았고, 아래 URL은 모두 `key=***`로 가렸습니다. 명세상 인증은 `key` 하나뿐이라 `APP_CLIK_API_ID`는 쓰지 않았습니다(이 환경에 설정돼 있지도 않았습니다).

- **CLIK 호출은 모두 282번 시도했고, 그중 257번이 서버에 닿았습니다**(한도 1,000회/일, 이번 작업 상한 300회). 닿지 않은 25번은 TLS 핸드셰이크 단계에서 끊긴 것입니다(§1).
- 이 컨테이너에는 Docker가 없어 PostgreSQL 16(pgvector)과 Redis를 직접 띄웠고, CI와 같게 `tesseract-ocr`·`tesseract-ocr-kor`·`fonts-nanum`을 설치했습니다.

## 요약

- **받은 그대로의 어댑터는 0건을 가져왔습니다.** 목록 호출 1번은 "성공"으로 끝났지만 레코드는 0건이었습니다. 응답은 봉투 객체 하나가 든 **배열**이고 행은 `LIST[].ROW` 안에 있는데, 어댑터는 배열의 원소(봉투)를 행으로 읽었고, 봉투에는 `DOCID`가 없어 모두 버렸습니다. 추정해 둔 날짜 파라미터(`startDate`·`endDate`)는 명세에 없고, 서버는 오류 없이 무시했습니다.
- **경로(`/openapi/minutes.do`), 필드명(`DOCID`·`MTG_DE`·`RASMBLY_NM`·`MINTS_HTML` 등), 상세 호출(`displayType=detail&docid=`)은 추정이 맞았습니다.** 틀린 것은 봉투 모양, 날짜 필터, 결과 코드 처리, 그리고 명세에 없는 두 가지였습니다. 하나는 한 회의의 **수정본마다 DOCID가 따로** 있다는 것, 다른 하나는 성남시의회처럼 `MINTS_HTML`에 **의회 누리집 페이지 전체**를 넣는 곳이 있다는 것입니다(§3).
- **성남시의회 대조(§4)**: 2025-09-01 ~ 2026-09-28의 본회의·예결특위는 CLIK에도 누리집 크롤링과 **똑같이 34개 회의**가 있었습니다(한쪽에만 있는 회의 0). 다만 DOCID는 110개였습니다. 누리집 본문의 20자 이상 줄 21,033개 중 20,579개(97.8%, 계산)가 CLIK 본문에 그대로 있고, 의원 발언 줄 수는 34개 회의 모두 같습니다(합계 6,670). 신호는 누리집 75건, CLIK 72건이고 32개 회의에서 같았습니다. 차이의 대부분은 CLIK이 준 판이 교정 전 임시본이라 "주요사업비 **예반** 반영 내역"처럼 오타가 남아 있었기 때문입니다.
- **전국 적재(§5)**: 최근 14일, 이어서 30일 창으로 전 의회를 받았습니다. 30일 창의 목록은 1,000행(772개 회의)이었고, 호출 상한 때문에 최신 178개 회의(52개 의회, 회의일 2026-09-09 ~ 09-21)만 상세까지 받았습니다. **178건 모두 `CN-` 의회로 풀렸습니다(exact).** 신호는 267건입니다.
- **다른 의회의 발언자 표기(§6)**: 전국 178건 중 109건이 의원을 "○최광선 의원"처럼 **이름과 의원 사이를 띄어** 적습니다. 기존 규칙은 이를 직함 "최광선" + 이름 "의원"으로 읽어, 신호 318건 중 92건이 의원의 요구를 집행부의 약속으로 읽은 것이었습니다. 고친 뒤 267건 중 0건입니다.
- `pytest` 382개 통과(369 → 382, 건너뜀 0). `manage eval all`의 JSON은 새 DB에서 main과 차례로 돌려 바이트까지 같습니다(값 148개, SHA-256 `a950a3cd…`).

## 1. 명세와 호출 기록

### 1.1 명세 읽기

`clik.nanet.go.kr/robots.txt`는 `User-agent: *` / `Allow: /`입니다. 첫 화면 바닥글의 "Open API" 링크(`/potal/guide/resourceCenter.do`)에 회의록·의안·의원·정책정보의 요청 주소, 요청 인자, 출력 값, 예제, 오류 코드표, 지방의회 ID 목록(243곳)이 모두 있습니다. 명세는 이 페이지에서 읽었고, 따로 허용할 호스트는 없었습니다. 페이지 요청은 3번(robots.txt, 첫 화면, 안내 페이지)이고 첫 화면을 받기 전에 TLS 끊김이 한 번 있었습니다.

회의록 명세의 요점입니다.

| | 목록 (`displayType=list`) | 상세 (`displayType=detail`) |
|---|---|---|
| 필수 | `key`, `type`(xml·json), `startCount`, `listCount`, `searchType`(`ALL`·`MTR_SJ`·`MINTS_HTML`·`RASMBLY_NM`·`PRMPST_CMIT_NM`) | `key`, `type`, `docid` |
| 선택 | `searchKeyword`, `rasmblyId`(지방의회 ID), `sort`(`WEIGHT/DESC`·`MTG_DE/ASC`·`MTG_DE/DESC`) | |
| 출력 | `SERVICE`, `RESULT_CODE`, `RESULT_MESSAGE`, `TOTAL_COUNT`, `LIST_COUNT`, `DOCID`, `RASMBLY_ID`, `RASMBLY_NM`, `RASMBLY_NUMPR`(대수), `RASMBLY_SESN`(회수), `MINTS_ODR`(차수), `MTGNM`(회의명), `MTG_DE`(회의일) | 목록 필드 + `MTR_SJ`(안건), `MINTS_HTML`(회의록 HTML), `ORGINL_FILE_URL`(원본 파일 URL) |

- **날짜 필터가 없습니다.** 창을 정하려면 `sort=MTG_DE/DESC`로 최신부터 읽다가 창보다 오래된 회의가 나오면 멈춰야 합니다.
- 오류 코드: `ERROR01` 인증키 무효, `ERROR02`~`08` 각 파라미터 무효, `ERROR09` 일별 허용 트래픽 초과, `ERROR10` 사용불가 키, `ERROR11` 호출 중 오류.
- 성남시의회의 ID는 `031013`입니다.

### 1.3 응답 모양

```json

  "TOTAL_COUNT": 7338, "LIST_COUNT": 2,
```

- 성공은 **원소 하나짜리 배열**, 오류는 배열이 아닌 **객체 하나**입니다. 둘 다 HTTP 200입니다.

## 2. 받은 그대로의 어댑터

`sources.config`에 `{"council_ids": ["031013"]}`만 넣고 30일 창으로 `manage sources ingest -s clik_minutes`를 돌렸습니다. 첫 실행은 세 번 모두 `ConnectTimeout`이었고(상한 3), 두 번째 실행은 **호출 1번, `succeeded`, 가져온 것 0**이었습니다. 코드의 원인은 셋입니다.

1. `_rows`가 배열을 받으면 그 원소를 그대로 행으로 돌려줬습니다. 원소는 봉투라 `DOCID`·`MTG_DE`가 없어 전부 버려졌습니다. 실제 행은 `LIST[].ROW` 안에 있습니다.
2. 날짜 창을 `startDate`·`endDate`로 보냈지만 명세에 없는 파라미터입니다. 서버는 무시하고 전체 목록을 줍니다. 고치지 않았다면 페이지 이동이 창과 상관없이 전 기간을 훑었을 것입니다(성남 7,338건이면 74쪽(계산)).
3. `RESULT_CODE`를 보지 않아, 틀린 키(`ERROR01`)도 "0건 성공"으로 끝났을 것입니다.

## 3. 명세에 없던 것

### 3.1 한 회의에 DOCID 여러 개

성남시의회 창 안의 본회의·예결특위 행은 110개인데, (회수, 회의명, 차수, 회의일)로 묶으면 34개 회의입니다. 한 회의에 DOCID가 1개인 곳이 7개, 가장 많은 곳은 9개(제308회 본회의 제2차)입니다. 상임위까지 합한 창 전체로는 495행, 165개 회의입니다(계산).

제305회 본회의 제2차(2025-09-22)의 8개를 모두 받아 봤습니다. 본문(HTML → 텍스트)은 77,346 ~ 79,904자이고, 둘은 글자까지 같았으며, 셋에만 `ORGINL_FILE_URL`이 있었습니다. 목록에는 판을 가를 필드(등록일, 판 번호)가 없고, DOCID 숫자도 본문 길이 순서와 맞지 않았습니다. 제312회 본회의 제2차의 두 DOCID는 띄어쓰기 교정("주민발의" ↔ "주민 발의", "소외 지역" ↔ "소외지역")과 한 구절의 편집만 달랐습니다.

어댑터는 목록을 회의 단위로 묶고, **회의마다 첫 번째로 나온 DOCID 하나만** 상세를 부릅니다. 문서의 외부 ID는 DOCID가 아니라 회의(`031013:10:312:2:20260907:본회의`)이고, 묶인 DOCID는 모두 `structured.revision_docids`에 남깁니다. 이미 저장된 회의는 상세를 부르지 않습니다. 같은 창을 다시 돌리면 목록 5번(+연결 재시도 2)만 쓰고 상세는 0번이었습니다. 고른 판이 최종본이라는 보장은 없습니다. 성남 34건 중 20건의 본문 첫머리에 "[본 회의록은 최종 교정 전 임시회의록이므로 법적 효력이 없습니다]"가 있었습니다. 판이 바뀌면 다시 받는 기능은 넣지 않았습니다(하루 1,000회 한도에서는 판마다 상세를 부를 수 없어서).

### 3.2 `MINTS_HTML`이 누리집 페이지 전체인 곳

성남시의회의 `MINTS_HTML`은 누리집 회의록 뷰어 페이지 그대로입니다. `<header>`, `<nav>`, 사이드바(`<aside>`, 검색 `<form>`), 글꼴·글자 크기·줄 간격 선택(`<select>`)이 본문 앞에 있어, 기존 `html_to_text`로는 "Toggle navigation", "굴림", "10pt" … "240%" 같은 줄 수십 개가 회의록 앞에 붙었습니다. 은평구의회 예제(명세 페이지)처럼 본문만 주는 곳도 있습니다.

발언자는 `<strong>○<a …>박기범</a>의원</strong>&nbsp;&nbsp;존경하는 …`처럼 굵은 글씨 뒤에 공백 두 칸으로 적습니다. 기존 변환은 연속 공백을 한 칸으로 줄여 "○박기범의원 존경하는"이 되었고, 이는 [회의록 실데이터 §4의 1](real-data-minutes.md#4-고친-것)에서 고친 바로 그 문제(의원을 직함으로 읽음)를 다시 만듭니다.

- 같은 문장은 글자까지 같습니다. 예: 제307회 본회의 제1차(2026년 예산안 제안), 양쪽 모두 "…기금 전출금 234억 원, 수내교 전면 개축공사 105억 원, 상대원2동·이매1동·…".
- **차이는 판입니다.** CLIK 쪽은 첫 DOCID를 골랐고, 20건이 교정 전 임시본이었습니다. 제309회 본회의 제1차(2026년 제1회 추경 제안)에서 CLIK 판은 "주요사업비 **예반** 반영 내역으로는 판교 시스템반도체 연구센터 조성 263억 원, …"이고 누리집 HWP는 "주요사업비 **예산** 반영 내역으로는 …"입니다. 규칙 기반 추출기는 "예산 반영 내역" 머리말로 목록을 알아보므로 이 회의의 신호가 누리집 5건, CLIK 1건이 됐습니다. 신호 수가 다른 회의는 이것과 제307회 본회의 제2차(11 ↔ 12) 둘뿐입니다.
- CLIK의 `ORGINL_FILE_URL`이 있는 21건 중 12건은 그 key가 누리집 크롤러가 받은 HWP의 key와 같았습니다. 나머지 9건은 CLIK이 다른 판의 key를 가리킵니다.
- 누리집 HWP에는 "임시회의록" 문구가 없었습니다(누리집 목록의 링크 글자는 "[임시] 본회의"였음).

### 4.4 무엇을 어느 쪽에서 얻나

- **CLIK에만 있는 것**: 회기·차수·회의명·회의일이 필드로 옵니다(누리집은 링크의 `title` 속성을 정규식으로 읽음). 호출 40번에 34.4초, 누리집은 요청 88번에 134.9초였습니다. HTTPS로 받습니다(누리집은 HTTPS가 거의 다 끊겨 HTTP로 받았음). 그리고 전국 243개 의회가 같은 모양입니다.
- **누리집에만 있는 것**: 지금 누리집이 보여 주는 판(HWP)입니다. CLIK은 어느 DOCID가 최종본인지 알려 주지 않습니다. 가장 최근 회의도 누리집이 빠를 수 있습니다. CLIK에 들어 있는 성남시의회의 가장 최근 회의는 2026-09-07이었습니다.
- 이번 창에서는 **어느 쪽도 상대가 가진 회의를 놓치지 않았습니다.**

## 7. 고친 것

코드는 `sources/clik.py`, `sources/base.py`, `pipeline/ingest.py`, `pipeline/backfill.py`, `sources/check.py`, `cli.py`, `parsing/chunking.py`, `llm/providers/heuristic.py`입니다. 테스트는 실제 응답을 줄여 만들었습니다(`tests/unit/test_clik.py`, 키 제거).

1. **봉투와 행.** 배열의 첫 객체를 봉투로 읽고 `LIST[].ROW`에서 행을 꺼냅니다. `RESULT_CODE`가 `SUCCESS`가 아니면 `ERROR09`는 한도 소진(KST 자정 이후 재예약), `ERROR11`은 일시 오류, 나머지(`ERROR01`~`08`, `ERROR10`)는 즉시 실패입니다. 오류 메시지에 키는 들어가지 않습니다.
2. **날짜 창.** 날짜 파라미터를 빼고 `sort=MTG_DE/DESC`로 100행씩 읽다가, 한 쪽에 창보다 오래된 회의가 나오면 멈춥니다. 창 밖 행은 버립니다.
3. **회의 단위로 묶기**(§3.1). 외부 ID는 `의회ID:대수:회수:차수:회의일:회의명`(128자를 넘으면 회의명을 해시로)이고, 회의마다 상세 1번, 저장된 회의는 0번입니다. 저장 여부는 `run_ingest`가 어댑터에 조회 함수를 넘겨 알려 줍니다(`SkipsStored`).
4. **선택 설정**: `meeting_pattern`(회의명 정규식, 예: `본회의|예산결산`), `max_details`(한 번에 부를 상세 수 상한).
5. **제목과 필드.** 제목은 "경기도 성남시의회 제312회 본회의 제2차 (2026-09-07)"입니다(차수 0은 생략). 문서 URL은 CLIK 포털의 회의록 화면, `structured`에 의회 ID·대수·회수·차수·회의명·DOCID·수정본 DOCID·원본 파일 URL을 남깁니다. 안건(`MTR_SJ`)은 넣지 않았습니다.
6. **HTML → 텍스트**(§3.2). `header`·`nav`·`aside`·`form`·`select`·`button`·`script`·`style`·`noscript` 안은 버리고, `○`로 시작하는 굵은 글씨 뒤에는 공백 두 칸을 둡니다. 줄 끝 공백도 지웁니다. 기존 테스트(`test_html_to_text_keeps_speaker_lines`)는 그대로 통과합니다.
7. **띄어 쓴 의원 표기**(§6).
8. **`manage sources check -s clik_minutes`**: 최신 목록 1쪽과 그 첫 회의의 상세, 2번을 불러 조달청 점검과 같은 표로 보여 줍니다. `--council 031013`으로 의회를 고를 수 있습니다. 적재 보고서에는 CLIK의 `sent`·`retries`·`errors`와 어댑터 통계(`minutes`)가 들어갑니다.

- 검증: `ruff check`, `ruff format --check`, `mypy`(strict) 통과, `pytest` 382개 통과(건너뜀 0, main 369). pytest는 `APP_LLM_PROVIDER=heuristic`으로 돌렸습니다. 이 환경의 기본값(`anthropic`)으로 처음 돌렸을 때는 통합 테스트 8개가 실제 API를 불렀다가 "credit balance is too low"로 거절되어 실패했고, 비용은 들지 않았습니다.
- `manage eval all`: main과 이 브랜치를 각각 새 DB(마이그레이션 → `seed --anchor 2026-09-25` → `demo run`)에서 차례로 돌렸고, JSON이 바이트까지 같습니다(값 148개, SHA-256 `a950a3cd96f8…`). 합성 회의록은 평문이고 "○위원 박지훈" 모양이라 이번 변경의 영향을 받지 않습니다.

## 8. 남은 일

1. **판 고르기.** 첫 DOCID가 교정 전 임시본인 경우가 성남 34건 중 20건이었고, 그 오타("예반") 때문에 신호 4건을 놓쳤습니다. 수정본 DOCID를 모두 저장해 두었으므로, 한도에 여유가 있을 때 "임시회의록" 문구가 있는 회의만 다른 판을 받아 보는 방법이 있습니다.
2. **수집 창과 지연.** CLIK에는 회의록이 1~2주 늦게 올라옵니다(§5). 매일 수집의 겹침(3일)을 CLIK만 14일 이상으로 늘리는 것이 필요해 보입니다. 저장된 회의는 상세를 부르지 않으므로 겹침을 늘려도 드는 것은 목록 호출뿐입니다.
3. **전국 백필.** 한 달이 상세 약 770번(계산)이라, 여러 날에 나눠 받아야 합니다. `max_details`로 하루 몫을 정할 수 있습니다.
4. 발언자 표기 중 "○위원장 최혜연 : …"(쌍점), "○의장 이복형"(발언이 다음 줄) 같은 모양은 대부분 읽히지만 따로 재지 않았습니다. "○…위원장"을 의원으로 볼지는 [회의록 실데이터 §6](real-data-minutes.md#6-회의록-신호-20건-수기-대조)처럼 여전히 정하지 않았습니다.
5. 규칙 기반 추출기의 사업명·금액은 전국 표본에서도 약합니다(§5). LLM 추출기로 같은 문서를 돌리는 것은 비용 추정(`--dry-run`) 뒤 사람이 한도를 정해 합니다.
