# 코드 반영과 실데이터 검증 상태

2026-09-30 갱신. 코드의 수정·검증과 실제 운영 반영을 구분한다. 이 문서는 배포 성공을 주장하지 않는다.

사용자가 공개 데모를 직접 맡는다고 범위를 확정했다. 이번 후속 작업은 저장소의 기능·데이터 품질·검증 보완이며, 공개 데모 호스팅이나 유료 인프라 생성은 포함하지 않는다.

## 후속 보완

- 사업과 개별 계약을 별도의 기회로 유지하며 검토된 1:N 관계를 저장한다. 관리자 `/admin/relations`에서 양쪽 원문을 확인하고 판정하며, 버전 충돌·중복 요청·순환·기관 불일치를 검사한다. 원문이 달라지면 확정 표시를 재검토 상태로 바꾸고 기존 판정 이력은 보존한다. 과거 혼합 기회는 감사 목록으로 제공하며 자동 분해하지 않는다.
- 예산 분야를 제목과 실제 구매 용도 중심으로 분류하고 편성목·이웃 행의 오염을 줄인다. 모호한 분류는 검토 대상으로 남긴다. 관리자는 분야를 정정할 수 있고 수정 이력이 평가자료에 포함된다. [회귀 측정 범위와 비용](budget-classification-regression.md)을 참조한다.
- 같은 사업명이더라도 명시된 관할 구가 다르면 예산 행을 자동 병합하지 않는다. 부서 이름 변경만으로 동일 사업을 차단하지 않는다.
- CLIK의 저장된 회의는 요청 종료일 기준 기본 30일 역조회에서 새 DOCID를 확인하고, 검토한 원문은 기존 보호 경로로 보존한다. `revision_lookback_days`로 기간을 조정하며 명시한 더 넓은 backfill은 유지한다. 요청 기간 밖의 미수집 회의는 역조회만으로 가져오지 않는다. 새로 관측한 판을 최종 확정본이라고 가정하지 않으며, 역조회보다 오래된 수정판은 회의일을 포함한 수집 기간이 필요하다.
- `manage sources coverage`는 기관별 설정·실제 수집·원문 가용성·공개일 근거와 실패 상태를 구분한다. 전역 API 설정 하나로 전국 수집 완료를 표시하지 않는다. 로컬 파일의 읽기 가능 여부와 원격 파일의 미검증 상태를 구별한다.
- `manage eval export-reviews`는 원문·해시·근거 위치·사람의 실제 판정 범위를 고정한다. 문서와 같은 내용은 같은 분할에 배치하고, 근거 없는 승인 사례는 제외 사유를 남긴다. 승인 클릭만으로 모든 필드가 독립 정답이 되지 않는다.
- `manage eval freeze`는 현재 시점의 입력·연결·예측을 일관된 읽기 전용 DB 스냅샷으로 보관한다. 과거 상태를 소급 생성하지 않으며, 누락된 원문·벡터와 코드 리비전의 운영자 제공 여부를 표시한다.
- 재연결 감사는 공개일순·예산우선·역순을 비교한다. 역순은 연결기 내부 정렬로 원래 순서가 복원되지 않도록 건별로 전달한다. 결과가 같다는 사실과 정답이라는 주장을 구분한다.

## 수집 순서 민감도 보완 (PR #54)

[PR #54](https://github.com/sokldjs554/procurement-forecast/pull/54)는 기관별 정규 재조정,
중단 후 자동 복구, 추천 등록의 영속 세대 확인, 고객의 최초 근거 보존을 추가합니다.
기존 증거를 고정한 뒤에도 발주계획·입찰 근거는 계속 연결하고 다시 평가합니다.
사람 판정과 관계 이력은 자동으로 바꾸지 않습니다. 이미 발행된 브리프·알림과
피드백은 보존하며, 현재 추천 점수는 새 근거에 맞춰 갱신합니다.

기존 고객 이력만 있고 원본 근거 표가 아직 비어 있는 자료도 재추출 전에 보호합니다.
기회 행 잠금으로 피드백·브리프·알림 발행과 자동 연결을 직렬화하며, 진행 중인
사용자 작업과 충돌한 재조정은 부분 적용 없이 재시도합니다.

[CI](https://github.com/sokldjs554/procurement-forecast/actions/runs/36666923090)의
실제 PostgreSQL/Redis 테스트 **782개 전부 통과(테스트 skip 0)**, 웹 **61개**, 브라우저
**3개**, 정적 검사·OpenAPI 일치·Terraform·API/웹/Render 이미지 빌드가 통과했습니다.
검증 코드는 `9834b6a`이며 테스트용 병합은 `92f7afc`입니다. 삽입·도착·배치 순서 조합,
고객 최초 근거 이후 여섯 도착 순서, 동시 사용자 작업 잠금과 중단 복구를 검증했습니다.
기존 합성 추출 P/R **1.000/1.000**, 연결 **1.000/0.985**, 보정 OCR CER **0.0099**,
금액 토큰 **1.000**, 수기54사례 P/R **0.929/0.520**을 유지했습니다.

운영 규모에서 보호 조회가 64~72초 걸리는 병목을 발견해 병합을 보류하고 수정했습니다.

대상·보호 조건을 줄이지 않았고 성능과 hit/miss 행 수를 CI 기준에 추가했습니다.
[최종 전후 감사](https://github.com/sokldjs554/procurement-forecast/actions/runs/36666923259)도
통과했습니다. 입력 2,404신호 중 2,399신호가 공개일순·예산우선·역순 모두
**1,323묶음**으로 수렴했고, 순서별 소속 차이는 **6/89개 → 0/0개**입니다.
각 코드의 독립 DB 반복 결과도 바이트까지 같습니다. 기준 대비 소속이 바뀐 35신호를

변경 **138/131초**였습니다. [실행 계획과 비용](performance.md)을 함께 확인합니다.
이 결과와 기존 전후 평가 JSON은 모두 보존한 실행 결과를 대조한 수치입니다.
[운영 적용 명령과 보존 조건](order-independent-linking.md)을 참조하세요.
마이그레이션 `0004`와 worker sweep이 기존 자료도 완료 단계로 가져옵니다.
이 문서의 CI 검증은 외부 운영 DB 마이그레이션을 실행했다는 뜻이 아닙니다.

## 실제 운영 대상 조회 (2026-09-30)

사용자가 확인한 Render `My workspace`에서 서비스를 직접 조회했다. 조회된 서비스
18개 중 `sokldjs554/procurement-forecast` 저장소에 연결된 서비스는 **0개**였다.
등록된 PostgreSQL 1개와 Key Value 1개도 다른 프로젝트용이었다. 이름이 비슷한
`procure-delta-demo`는 `sokldjs554/procure-delta`의 정적 데모 빌드이며 이 프로젝트의
운영 API·worker가 아니다. 해당 자원은 변경하지 않았다.

GitHub에서 조회 가능한 Actions 실행 233건에도 `Deploy (Cloud Run)` 실행은 없었다.
이 조회만으로 수동 생성한 외부 GCP 환경까지 없다고 단정하지는 않는다. 현재 연결로는
이 프로젝트의 실제 운영 DB나 배포 대상이 확인되지 않았으며, 마이그레이션 `0004`를
외부 운영 DB에 적용한 사실도 없다.

[PR #54](https://github.com/sokldjs554/procurement-forecast/pull/54)와 검증 문서는 main에
반영됐다. 반영 후 [CI](https://github.com/sokldjs554/procurement-forecast/actions/runs/36668672260)도
통과했다. 저장소의 [Render 구성](render-deployment.md)은 새 유료 자원을 만드는
설정이며, 기존 서버를 갱신한 결과가 아니다. 실제 적용에는 올바른 운영 대상 또는
신규 인프라 생성 범위·비용 승인과 필요한 운영 설정이 필요하다. 공개 데모는 사용자가
맡는 기존 범위를 유지한다.

## 확인한 코드 반영과 검증

[PR #50](https://github.com/sokldjs554/procurement-forecast/pull/50)을 main의 `1519ec9`에 반영했고,
병합 파일 트리가 검증한 `153f2bc`와 같음을 확인했습니다. 공개 데모 변경을 포함한 PostgreSQL/Redis
통합 테스트 **551개**, 웹·브라우저·이미지 빌드, 실데이터 두 번의 재연결과 대용량 쿼리 벤치가 통과했습니다.
전후 평가와 실행 링크는 PR에, SQL 실행 계획과 재연결 시간의 비용은 [성능 보고서](performance.md)에 있습니다.
이것은 코드 검증이며 아래의 운영 배포 완료를 뜻하지 않습니다.

## 실행 환경의 경계

공개 데모 호스팅은 사용자가 진행한다. 선택 가능한 Render 설정과 런북은 저장소에 남겨 두었지만 이번 후속 작업의 배포 대상으로 사용하지 않았고 유료 자원을 생성하지 않았다. 저장소 반영과 CI 실행을 실제 운영 DB의 마이그레이션·원문 수집 성공으로 표현하지 않는다. 저장소의 실신호 아카이브에는 전체 원문이 없으므로 이를 운영 원문 DB 대신 사용하지 않는다.

## 기존 원문 재검증

운영 DB 백업과 쓰기 작업 중지를 확인한 뒤, 같은 날짜·범위로 실행한다. 먼저 반환된 `counts`, `issues`, `examples`, `manual_review_required`를 검토한다.

```sh
manage pipeline revalidate --source clik_minutes --today 2026-09-29 --out audit.json
manage pipeline revalidate --source clik_minutes --today 2026-09-29 \
  --apply --expected-digest '<audit.json의 digest>' --out applied.json
```

`has_more`가 참이면 반환된 `next_after_id`를 다음 실행의 `--after-id`로 사용한다. 각 페이지마다 dry-run을 먼저 실행한다. 데이터·설정·판정이 바뀌면 기존 digest 적용은 거절된다. 테이블 쓰기 잠금은 최대 5초 대기 후 실패하므로 유지보수 시간에 실행한다. 이 명령은 새로운 알림을 보내거나 유료 모델을 호출하지 않는다.

사람이 검토한 문서의 원문이 바뀌면 수집도 명시적으로 실패한다. 현재 정책은 그 수집 트랜잭션 전체를 롤백해 기존 원문과 검토를 보호하는 것이다. 운영자는 변경 원문과 기존 판정을 비교하고 명시적인 이행 방법을 정해야 한다. 보호를 끄거나 검토 기록을 삭제해 수집을 강제로 진행하지 않는다.
