# 실데이터 30일 적재와 측정 (2026-09-26)

첫 점검([`source-check.md`](source-check.md))은 오퍼레이션마다 첫 페이지 한 번만 불러 봤습니다. 이번에는 실제 조달청 데이터 30일치를 DB에 넣고, 파이프라인(처리 → 연결)을 끝까지 돌려 봤습니다. 이 문서의 숫자는 전부 이 실행에서 직접 잰 것이고, 계산으로 낸 값에는 따로 표시했습니다.

- 기간: 등록일 2026-08-28 ~ 2026-09-26 (30일), 발주계획·사전규격·입찰공고 × 용역·물품·공사 9개 오퍼레이션
- 환경: 개발 컨테이너의 PostgreSQL 16.13 + pgvector 0.6.0, Redis 7.0, 4 CPU. data.go.kr은 컨테이너의 프록시를 거쳐 호출했습니다.
- 경로: 워커의 `ingest_source` → `process_document` → `link_signals`와 같은 코드를 한 프로세스에서 돌리는 명령 두 개를 추가했습니다. 어댑터와 파이프라인 단계는 그대로 쓰고, 호출 예산만 덧붙였습니다.

```bash
cd apps/api
APP_DATA_GO_KR_DAILY_QUOTA=500 \
  uv run manage sources ingest -s g2b --days 30 --rows 999 --max-calls 250 --report run.json
uv run manage pipeline run       # 처리 대기 문서를 모두 처리하고 새 신호를 연결
```

`--max-calls`는 이번 실행의 서비스별 상한이고, `APP_DATA_GO_KR_DAILY_QUOTA`는 Redis에 남는 하루치 상한입니다. 재시도도 한 번으로 셉니다. 이번에는 두 번째·세 번째 적재까지 합쳐도 서비스마다 500회를 넘지 않도록 각각 250과 500으로 걸었습니다.

| 번호가 하나도 없는 입찰공고 | 6,334 (23.1%) |

| 공고번호 목록이 있는 발주계획 (모두 그 공고가 적재됨) | 12,707 |

- **원래 비어 있는 번호**가 있습니다. 사전규격 응답에는 발주계획번호 필드가 아예 없어서, 사전규격 ↔ 발주계획은 둘 다를 가리키는 입찰공고를 거쳐서만 이어집니다(5,453건). 공사 사전규격은 한 달에 205건뿐이라, 공사 입찰공고의 사전규격번호도 대부분 비어 있습니다.
- 발주계획의 공고번호 목록은 대부분 입찰공고의 발주계획번호를 거꾸로 적은 것입니다. 목록으로만 이어지는 계획은 7건이었습니다.
- **발주계획이 먼저 오지 않는 경우가 많습니다.** 30일 안에 이어진 발주계획 → 입찰공고 14,040쌍의 간격은 이렇습니다.

  |---|---:|---:|---:|---:|---:|
  | 건수 | 7,039 | 4,993 | 1,472 | 536 | 0 |

  이 밖에 6,143건은 30일보다 먼저 등록된 발주계획을 가리킵니다. 30일 창이라 긴 간격은 잘려서 보이지 않는 것이고, 1년치를 받아야 제대로 된 분포가 나옵니다. 사전규격 → 입찰공고 6,129쌍은 중앙값 7일, 90백분위 14일이었습니다.

## 7. 남은 문제와 다음 단계

- **기관 사전**: 조달청 수요기관코드로 식별하도록 바꿔 연결 대상이 4.8%에서 95.0%가 됐습니다([§8](#8-기관-사전-전체와-조달청-코드)). 이제 남은 건 사전이 모르는 지자체입니다. "전남광주통합특별시" 1,965건과 인천 새 구 95건이 검토 대기에 있고, 사전규격에만 나오는 이름 654건(한국수자원공사 272건 등)은 코드가 없어 풀 방법이 없습니다.
- **취소공고**: 1,738건이 "공고 나옴"으로 처리되고 있었습니다. 이제 이렇게 처리합니다.
  - 취소공고는 같은 공고번호의 다음 차수로 오므로, 그 번호의 공고를 거둬들인 것으로 봅니다. 같은 번호로 나중에 재공고가 오면 다시 살아나고, 같은 날이면 취소를 우선합니다.
  - 기회의 단계와 상태는 남은 신호로 다시 계산합니다. 앞선 발주계획이나 사전규격이 있으면 "공고 전"으로 돌아가고, 공고와 그 취소밖에 없으면 끝난 입찰(`closed`)이 됩니다.
  - 같은 공고번호의 다른 차수(변경·재공고·취소)는 제목이나 금액이 바뀌어도 번호로 같은 기회에 묶습니다. 전에는 유사도에만 맡겼습니다.
  - 이 처리를 넣은 뒤로 30일치를 다시 재지는 않았습니다. 공고 종류가 문서에 새로 담기므로, 다음 적재 때 입찰공고는 한 번씩 "변경"으로 다시 처리됩니다.
- **기회 병합**: 입찰공고가 이미 따로 만들어진 두 기회(발주계획 쪽, 사전규격 쪽)를 번호로 가리키면 둘을 합쳐야 합니다(B에서 9건).
- **1년치 적재**: 리드타임 분포를 제대로 보려면 발주계획을 1년치 받아야 합니다. 이번 비율이면 약 21만 건이고, 오퍼레이션·주마다 999건 페이지 두 장이라 300회 남짓입니다(계산). 개발 키 하루 한도 안에 들어갑니다.
- 분류 체계를 조달 전반으로 넓히는 일, 괄호 머리표 정규화, 단가계약·1인당 단가 표시도 남았습니다.

## 8. 기관 사전 전체와 조달청 코드

§4에서 연결 대상이 4.8%에 그친 이유는 기관 사전이었습니다. [ADR-0011](adr/0011-provider-codes-for-institutions.md)대로 두 가지를 바꿨습니다. 지자체는 시도·시군구·의회·시도교육청까지 전부(506곳) 사전에 넣었고, 사전으로 풀리지 않는 조달청 레코드는 그 수요기관코드로 기관을 만들어(`G2B-<코드>`) 다음부터는 코드로 찾습니다. 그 뒤 같은 날(2026-09-26) 새 DB에 같은 30일(`--until 2026-09-26`)을 다시 넣고 파이프라인을 돌렸습니다.

- 적재: 88회 호출로 57,524건(발주계획 17,713 · 사전규격 9,286 · 입찰공고 30,525)을 받았습니다. 오류도 재시도도 없었고, 세 서비스 합쳐 747.4 s(계산) 걸렸습니다. 첫 적재보다 10건 많은 건 그사이 새로 등록된 레코드입니다.
- 환경은 §1과 같은 종류의 개발 컨테이너(PostgreSQL 16 + pgvector, Redis 7)입니다.

### 번호와 모순되는 연결이 다시 생긴 이유

B에서 0건이던 모순이 C에서 확정 52건 · 잠정 21건 나왔습니다. 번호로 검증할 수 있는 확정 유사도 연결 4,305건 중 52건(1.2%, 계산)입니다. 섞인 기회 195건을 열어 보니 두 가지였습니다.

- **180건은 유사도 연결이 끼어 있습니다.** 전형은 이렇습니다. 법무부 대전지방교정청이 "수용자 자비구매물품 생활용품(섬유유연제)" 사전규격과 "(샴푸, 린스, 폼클렌징)" 발주계획을 같은 날 냈습니다. 사전규격에는 발주계획번호가 없고 발주계획에는 사전규격번호가 없으니, 둘을 번호로 비교할 방법이 없어 유사도로 합쳐졌습니다. 며칠 뒤 샴푸 입찰공고가 발주계획번호로 이 기회에 붙었는데, 사전규격번호가 섬유유연제의 것과 달랐습니다. 번호를 가진 사업을 후보에서 빼는 §4의 규칙은 "같은 종류의 번호"끼리만 비교하기 때문에, 발주계획과 사전규격 사이는 막지 못합니다. 신호가 20배로 늘어 같은 기관의 비슷한 사업이 같은 창에 들어오는 일이 많아졌습니다.
- **15건은 번호 연결만으로 섞였습니다.** 제공처 데이터 자체가 그렇습니다. 충주시의 한 사전규격번호를 발주계획번호가 서로 다른 입찰공고들이 함께 가리키고 있었습니다(재해위험개선지구 정비 공고와 하수관로 정비 공고).

앞의 경우는 연결 단계의 한계라 이번에는 기록만 했습니다. 입찰공고가 나중에 다른 사전규격번호를 들고 오면 그 기회를 다시 나누거나, 번호 종류가 다른 신호끼리는 유사도 연결을 잠정으로만 두는 방법이 있습니다.

- 인천은 법정동 구성으로 확인했습니다. 옛 구성은 PublicDataReader 1.1.1에 들어 있는 법정동코드(마지막 생성일 2022-09-01)입니다. 제물포구 51개는 옛 중구의 내륙 44개와 옛 동구 7개를 합친 것입니다. 영종구 8개는 옛 중구의 나머지(중산·운남·운서·운북·을왕·남북·덕교·무의동)입니다. 서해구 11개와 검단구 10개를 합치면 옛 서구 21개와 정확히 같습니다.

### 해석에서 바꾼 것

- 새 시도 이름 "전남광주통합특별시"를 시도로 읽습니다. 가장 긴 이름부터 맞추므로, "전남광주통합특별시북구시설관리공단"이 "전남"(전라남도)으로 읽히던 것도 고쳐집니다. §8에서 전라남도로 잘못 들어간 `G2B-` 기관 44곳이 이 경우입니다. 데이터에 나오지 않은 줄임말은 넣지 않았습니다.
- 기관이 한때 속했던 시도도 그 기관의 시도로 봅니다. 옛 이름 별칭("전라남도 순천시")에서 읽어 둡니다. 그래서 "전라남도 순천시 스마트도시과"나 "광주광역시 동구청"처럼 별칭과 글자가 다른 옛 이름도 풀립니다.

- 합성 데모 세계는 순천시를 옛 표기 그대로 씁니다(`DEMO_SPELLINGS`). 사전 이름을 따라가게 두면 같은 시드로도 문서가 바뀝니다. `manage eval all`의 JSON은 main과 같습니다.

### `reresolve`와 새 적재가 같은가

두 DB의 문서 57,525건은 (수집원, 외부 ID)가 모두 같았고, **문서마다 기관도 모두 같았습니다.** 다른 건 두 가지입니다.

- `G2B-` 기관 44곳의 시도가 다릅니다. 이 기관들을 가리키는 문서는 233건입니다. `reresolve`는 기관이 없던 문서만 다시 풀고, 이미 저장된 `G2B-` 기관의 시도는 고치지 않습니다. 그래서 옛 DB에는 전라남도(46)로 남고, 새 DB에는 전남광주(12)로 들어갑니다. 지역 필터가 두 코드를 같은 시도로 보므로 추천에는 영향이 없습니다.
- 기회 수가 1개 다릅니다(27,508과 27,507). 연결은 처리 순서를 타는데, 이 1개를 따로 찾아보지는 않았습니다.

## 다시 돌리려면

```bash
make infra
cd apps/api && uv run manage db upgrade && uv run manage seed
APP_DATA_GO_KR_DAILY_QUOTA=500 uv run manage sources ingest -s g2b --days 30 --rows 999 --max-calls 250 --report run.json
uv run manage sources ingest -s g2b --days 30 --until <같은 날짜> --rows 999 --max-calls 250   # 멱등성
uv run manage pipeline run
uv run manage pipeline reresolve  # 새 DB라면: 사전규격이 입찰공고보다 먼저 들어와 놓친 이름을 다시 풂
uv run manage pipeline run
```

기관 사전을 새 법정동코드로 다시 만들 때는 `scripts/data/`에 새 스냅샷을 두고 `uv run python scripts/build_institutions.py scripts/data/<파일>`을 돌린 뒤, `manage seed`와 `manage pipeline reresolve`로 저장된 문서에 반영합니다.

적재는 수집원마다 끝날 때 커밋합니다. 한도나 오류를 만나면 그 수집원만 멈추고 받은 것까지는 남기며, 다음 수집원으로 넘어갑니다. 이때 종료 코드는 1입니다.
