# 0013. 긴 작업은 Postgres 큐로: 의미는 SQL 함수에, 테넌트 격리는 RLS로

## 맥락
파이프라인의 짧은 작업(수집·처리·연결·알림)은 arq(Redis) 큐가 돌립니다([0003](0003-arq-and-in-worker-cron.md)). 회의 영상 작업([0012](0012-meeting-video-as-minutes.md))은 성격이 다릅니다.
- 몇 분에서 몇 시간 걸립니다.
- 고객(테넌트)이 맡기고 돈을 냅니다.
- 진행률을 보여 줘야 합니다.
- 중간에 죽으면 이어서 해야 합니다.
- 취소할 수 있어야 합니다.
- 같은 영상을 두 번 맡기면 한 번만 해야 합니다.
- 작업이 끝날 때 사용량이 한 번만 과금돼야 합니다.

arq는 작업 상태를 Redis에 두어서, 작업·사용량·문서를 한 트랜잭션으로 묶거나 SQL로 테넌트별로 조회할 수 없습니다. 게다가 이 큐는 Python 단계 워커와 TypeScript 오케스트레이터(API·다운로드 워커)가 함께 씁니다. 두 언어에 큐 로직을 따로 두면 언젠가 어긋납니다.

## 결정
- **작업은 `jobs` 테이블에, 큐의 의미는 SQL 함수 `jobq_*`에 둡니다.** Python과 TypeScript는 이 함수를 부르기만 합니다.
  - `jobq_claim`: 준비된 작업 중 우선순위·대기 순서로 하나를 `FOR UPDATE SKIP LOCKED`로 가져옵니다. 워커가 여럿이어도 서로의 행 잠금을 기다리지 않습니다.
  - **리스와 하트비트**: 가져간 작업에는 리스(기본 60초)가 붙고, 워커가 하트비트로 연장하면서 진행률을 씁니다. 하트비트의 답이 `cancel`(취소 요청)이나 `lost`(리스 만료로 회수됨)이면 워커는 멈춥니다. `lost`일 때는 결과를 쓰지 않습니다.
  - `jobq_fail`: 재시도 가능한 오류는 지수 백오프에 equal jitter(절반 고정 + 절반 무작위)를 붙여 다시 대기열에 넣습니다. 시도 횟수를 다 쓰면 `failed`입니다. 예산 초과나 잘못된 입력처럼 재시도로 고칠 수 없는 오류는 바로 `failed`입니다.
  - `jobq_reap`: 하트비트가 끊긴(리스가 지난) 작업을 백오프를 붙여 되돌립니다. 워커가 주기적으로 부릅니다.
  - `jobq_cancel`: 작업과 그 아래 작업 전체를 취소합니다. 대기 중인 것은 바로, 실행 중인 것은 다음 하트비트에 멈춥니다.
  - **종료 신호를 받은 워커는 작업을 바로 반납합니다.** 리스가 끝나기를 기다리지 않습니다. 가져가기가 커밋된 직후부터 해당됩니다.
- **중복 제거**: 부분 유니크 인덱스 `(org_id, kind, dedupe_key) WHERE status IN ('queued','running','succeeded')`를 씁니다. 같은 영상(내용 해시)을 다시 맡기면 그 영상을 가진 작업을 돌려줍니다. 실패하거나 취소된 작업은 키를 풀어 줍니다.
- **체크포인트는 작업이 아니라 대상에 묶습니다**: `(org_id, 'video:<sha256>', key)`. 실패한 작업 대신 새 작업을 만들어도 끝난 창을 다시 전사하지 않습니다.
- **사용량은 추가 전용 `usage_events`에 씁니다.**
  - 작업 완료와 같은 트랜잭션에서 씁니다.
  - 멱등 키는 `job:<id>:<meter>`입니다. 두 워커가 같은 작업을 끝내도 한 번만 남습니다.
  - 미터: STT로 보낸 오디오 초(금액 포함), OCR 프레임, 계산 초.
- **예산은 오디오를 보내기 전에 봅니다.**
  - 영상 길이로 비용 상한을 계산합니다: (길이 + 창마다 2초의 겹침) × 분당 단가. 실제로 보내는 오디오는 이보다 많을 수 없습니다.
  - 이 상한이 작업 예산(`budget_usd`)을 넘거나, 이번 달(KST) 사용액과 합쳐 조직의 월 한도(`organizations.usage_cap_usd`)를 넘으면 STT를 한 번도 부르지 않고 실패시킵니다.
- **테넌트 격리는 RLS로 합니다.**
  - API는 요청마다 트랜잭션 안에서 `SET LOCAL ROLE app_tenant`와 `app.org_id`를 설정합니다. `app_tenant`는 테이블 소유자가 아니므로, 로그인 역할이 슈퍼유저여도 정책이 적용됩니다.
  - 정책: `jobs`는 자기 조직 행만 읽고 쓰고, `usage_events`는 읽기만 합니다. `api_keys`와 `job_checkpoints`는 권한도 정책도 없어 아예 보이지 않습니다.
  - `jobq_claim`·하트비트·완료·실패·회수 함수는 `PUBLIC`에서 실행 권한을 뺐습니다. 테넌트 세션은 큐를 돌릴 수 없습니다.
  - `app.org_id`를 설정하지 않은 테넌트 세션은 조회 자체가 오류로 끝납니다(fail closed).
  - 워커는 소유자 권한으로 모든 테넌트의 큐를 봅니다.
- **API 키**: `pfk_<8 hex>.<secret>` 형식입니다. 접두사와 비밀값의 SHA-256만 저장하고, 키는 만들 때 한 번만 보여 줍니다. 스코프는 `jobs:read`, `jobs:write`, `usage:read`입니다.
- **잠든 워커 깨우기**: 작업을 넣을 때 `pg_notify('jobq', kind)`를 보냅니다. 쉬는 워커는 `LISTEN`으로 바로 깨어나고, 알림을 놓쳐도 5초마다 폴링합니다.

## 결과
- 얻은 것 (통합 테스트 16개, 실제 PostgreSQL 16):
  - 같은 키는 같은 작업을 돌려줍니다. 실패한 작업의 키로는 새 작업이 생깁니다.
  - 같은 작업의 완료와 사용량 기록을 두 번 해도 사용량은 한 행입니다.
  - 한 워커가 행을 잠근 채 커밋하지 않아도, 다른 워커는 기다리지 않고 다음 작업을 가져갑니다.
  - 첫 재시도는 기준 20초일 때 10~20초 뒤로 밀립니다. 시도를 다 쓰면 `failed`입니다.
  - 리스가 지난 작업은 회수되고, 죽은 워커가 늦게 보낸 결과는 거부됩니다.
  - 테넌트 세션은 자기 작업만 봅니다. 다른 조직 행 쓰기, 큐 가져가기, 키 테이블 읽기는 모두 거부됩니다.
  - 실제 합성 회의 영상으로 돌린 작업:
    - 끝나면 신호(12~22초 근거)와 사용량 3행이 남고, 금액은 보낸 초 × 단가와 맞습니다.
    - 세 번째 STT 창에서 죽은 작업은 백오프 뒤 두 창을 건너뛰고 이어집니다.
    - 취소 요청을 받으면 멈추고 사용량을 남기지 않습니다.
    - 예산을 넘는 작업은 STT를 한 번도 부르지 않고 실패합니다. 월 한도도 이미 쓴 금액을 넣어 계산합니다.
    - 종료 신호를 받으면 1초 안에 대기열로 돌아갑니다. 커밋 직후의 좁은 틈도 포함합니다.
    - 리스를 잃은 워커는 결과도 사용량도 쓰지 않습니다.
  - 합성 평가 결과는 이 변경 전과 같습니다.
- 얻은 것 (TypeScript 오케스트레이터, `apps/orchestrator`, 테스트 30개):
  - API 키: 틀린 비밀값·폐기된 키·없는 스코프를 거부합니다.
  - 같은 URL이나 같은 `Idempotency-Key`는 같은 작업을 돌려줍니다.
  - 다른 조직의 작업은 조회·취소 모두 404입니다.
  - 월 사용량은 한국 시간 월 경계로 자기 조직 것만 합산합니다.
  - 다운로드: 연결이 끊긴 파일은 다음 시도에서 `Range: bytes=<받은 크기>-`로 이어 받아 해시가 원본과 같습니다. 허용 목록 밖으로의 리다이렉트(`169.254.169.254`), HTML 페이지, 크기 초과는 재시도 없이 실패합니다.
  - 워커 6개가 작업 24개를 두고 경쟁해도 각 작업은 정확히 한 번 실행됩니다.
  - 두 언어를 잇는 E2E(`scripts/e2e-media-queue.sh`, CI):
    1. API로 맡긴 합성 영상을 TypeScript 워커가 받습니다.
    2. Python 워커가 전사합니다.
    3. 확정 신호(2억 4천만원, 12.5~21.5초)와 사용량(36초)이 API로 보입니다.
- 치른 비용:
  - **큐가 둘입니다.** 파이프라인의 짧은 작업은 여전히 arq(Redis)입니다. 옮기는 비용보다 얻는 것이 작다고 봤고, 운영자는 두 곳을 봐야 합니다.
  - **처리량은 재지 않았습니다.** 영상 작업은 분당 몇 건 수준이라 `SKIP LOCKED` 한 번짜리 가져가기로 충분하다고 봤지만, 초당 수백 건을 넘는 규모에서는 확인하지 않았습니다.
  - **`NOTIFY`는 영속적이지 않습니다.** 알림을 놓치면 최대 폴링 주기(5초)만큼 늦게 시작합니다.
  - **마이그레이션에 역할 생성 권한이 필요합니다.** `CREATEROLE`이 필요하고, 없다면 관리자가 `app_tenant`를 먼저 만들어 둬야 합니다. 관리형 Postgres(Render)에서는 확인하지 않았습니다.
  - **워커가 공급자에게 보낸 호출이 중간에 끊기면** 그 요금은 사용량에 잡히지 않습니다. 체크포인트는 끝난 창만 남기 때문입니다. 분당 과금 STT에서는 우리가 떠안는 비용입니다.
  - **리스를 잃은 워커가 이미 문서를 넣었다면** 그 문서는 남습니다. 내용 해시가 같아 다음 워커의 입력은 `skipped`가 됩니다.

## 다시 볼 조건
- 파이프라인 작업도 고객별로 보여 주거나 과금해야 하면 arq 작업을 이 큐로 옮깁니다.
- 영상 작업이 분당 수백 건을 넘으면 가져가기를 여러 건 묶어 하고, 종류별 워커 풀로 나눕니다.
