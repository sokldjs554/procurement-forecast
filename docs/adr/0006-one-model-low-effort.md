# 0006. 추출 모델: 가장 좋은 모델 하나를 낮은 effort로

## 맥락
추출은 청크 수만큼 호출되는 대량 작업이고, 브리프는 사용자가 크레딧을 내고 요청하는 소량 작업입니다. 흔한 선택은 추출에 작은 모델, 브리프에 큰 모델입니다.

## 결정
- 추출과 브리프 모두 `claude-opus-5`를 쓰고, 비용은 **`output_config.effort`**로 조절합니다(추출 `low`, 브리프 `medium`). 모델이 하나면 프롬프트 캐시 네임스페이스도 하나이고, 평가해야 할 조합도 하나입니다.
- 추출 응답은 **structured outputs**(`output_config.format`, 엄격한 JSON 스키마)로 받습니다. 파싱 실패가 사라지고, Pydantic이 API가 강제하지 않는 숫자 범위를 다시 검사합니다.
- 고정 시스템 프롬프트(약 1.4k 토큰)는 `cache_control`로 캐시합니다.
- 비용 상한: (1) **트리아지** 로지스틱 모델이 신호 가능성이 낮은 청크를 LLM 없이 건너뜀(합성 세계에서 59%를 건너뛰고 정답 재현율 99%), (2) 청크 내용 해시 **캐시**, (3) Redis **일일 예산 가드**(초과 시 규칙 기반 추출기로 강등, `degraded`로 표시).
- 거부(refusal) 오탐(예: CCTV 조달 논의)은 서버 측 fallback으로 같은 호출 안에서 재시도하고, 그래도 실패하면 규칙 기반 추출기가 처리합니다.
- 키·권한·크레딧·모델 오류(`LLMSetupError`)는 강등하지 않고 추출을 멈춥니다. 모든 청크가 같은 이유로 실패하므로, 강등하면 배치 전체가 규칙 기반으로 조용히 끝나기 때문입니다. 작업은 실패로 남고 문서는 `pending`에 그대로 있어, 사람이 고친 뒤 다시 처리됩니다. 실제 회의록 실행에서 크레딧이 떨어졌을 때 드러나 2026-09-28에 바꿨습니다([real-data-minutes-claude.md §6.2](../real-data-minutes-claude.md#62-실행)).

## 결과
- 얻은 것: 운영 콘솔에서 작업·모델·프롬프트 버전별 비용, 캐시 적중률, 강등 비율을 봅니다. API 키가 없어도 전체 파이프라인이 규칙 기반으로 동작합니다(데모·CI).
- 치른 비용: 이 저장소의 수치는 규칙 기반 추출기로 측정했습니다. Claude 경로는 요청 형태·오류 매핑을 단위 테스트로만 검증했고, 실제 API로 평가 세트를 돌린 결과는 아직 없습니다.
- effort가 답을 바꾸므로 LLM 캐시 키에 모델과 함께 effort를 넣습니다. 넣지 않으면 effort를 올려도 이전 effort의 답이 계속 나갑니다.

## 다시 볼 조건
`manage eval llm`(→ [evaluation-llm.md](../evaluation-llm.md))이 이 결정을 검증하는 도구입니다. 같은 수기 세트를 Opus 5 `low`·`medium`, Sonnet 5 `low`, Haiku 4.5로 돌려 검증기 통과 후 정확도와 건당 비용을 나란히 봅니다.
- `low`와 `medium`의 차이가 작고 비용 차이가 크면 `low`를 유지하고, 차이가 크면 트리아지 임계값을 올려 호출 수를 줄인 뒤 `medium`을 씁니다.
- 더 작은 모델이 검증기 통과 후 같은 정확도를 내면 "모델 하나" 원칙보다 비용이 앞섭니다. 이때는 추출만 옮기고 브리프는 Opus 5에 둡니다.

## 측정 결과 (2026-09-26, 수기 세트 54건 · [evaluation-llm.md](../evaluation-llm.md))

| 추출기 | 재현율 | 분야 | 청크당 비용 | 캐시 읽기 |
|---|---:|---:|---:|---:|
| Opus 5 · low | 100% | 86.0% | $0.0107 | 92% |
| Opus 5 · medium | 100% | 90.0% | $0.0110 | 92% |
| Sonnet 5 · low | 98.0% | 87.8% | $0.0042 | 92% |
| Haiku 4.5 | 92.0% | 76.1% | $0.0046 | 0% |

- **low 유지.** medium은 나아진 필드 없이 비용만 3% 늘었습니다. 분야 정확도는 같은 설정의 두 실행 사이에서도 2~6%p 흔들려, 이 규모에서는 차이로 보지 않습니다.
- **Opus 5 low를 기본값으로 둡니다.** Sonnet 5 low는 비용이 39%이고 재현율이 1건 낮습니다. 이 제품에서 가장 비싼 오류는 놓친 신호입니다(고객이 몇 달 먼저 알 기회를 잃음). 50건으로는 1건 차이를 가를 수 없으니 기본값은 바꾸지 않습니다.
- **Haiku 4.5는 기대와 반대로 Sonnet보다 비쌉니다.** 시스템 프롬프트(약 1,400토큰)가 Haiku 4.5의 캐시 최소 길이(4,096토큰)에 못 미쳐 캐시가 걸리지 않습니다. 토큰 단가 표가 아니라 실측 비용으로 골라야 하는 이유입니다.
- **추출을 Sonnet 5 low로 옮기는 조건**: 추출 비용이 일일 예산 가드($25)에 닿을 때입니다. Opus 5 low 기준으로 하루 약 2,300 청크(트리아지 통과 기준)입니다. 브리프는 Opus 5에 그대로 둡니다. 전환하기 전에 실데이터 정답 세트로 재현율 차이를 다시 잽니다.
- **측정이 찾은 버그**: 첫 실행에서 검증기가 "2억 8천"을 200,008,000으로 읽은 파서 값으로 Claude의 맞는 답을 덮어썼습니다. "숫자는 파서가 최종 판정한다"는 규칙은 파서가 맞을 때만 안전합니다. 파서를 고쳤고(#10), 파서가 모델 값을 바꾼 횟수(`budget_replaced_by_parser`)를 평가표에 계속 남깁니다.
