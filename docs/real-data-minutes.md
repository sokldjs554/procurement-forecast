## 요약

- **처음으로 실제 회의록을 처리했습니다.** 성남시의회 본회의·예산결산특별위원회 회의록 34건(2025-09-12 ~ 2026-09-07, HWP 5, 1,859,805자)을 게시판 크롤러로 받았습니다(요청 88번, 132초, 오류 0). 따로 허용할 호스트는 없습니다.
- **HTTPS는 새 연결이 거의 다 끊겨 HTTP로 받았습니다(§1).** 정책 차단이 아니라 TLS 핸드셰이크에서 끊기며, 87번 중 2번만 연결됐습니다. openssl로도 서버의 TLS 버전·암호를 확인하지 못해 `legacy_tls_hosts`는 쓰지 않았습니다. 받은 파일마다 SHA-256을 남겼고, HTTPS로 다시 받아 대조하려던 60번은 모두 실패했습니다. 성남시 예산서 6권은 크롤러가 HTTPS로 받았고, 바이트 수·쪽수가 §8.4와 같습니다.
- **받은 그대로의 코드는 의원 발언을 하나도 알아보지 못했습니다(§4의 1).** 실제 회의록은 의원을 "○조우현위원"으로 적습니다. 그래서 신호 97건 중 58건이 의원의 요구("반영해 주시기 바랍니다")를 집행부의 약속으로 읽은 것이었습니다. 고친 뒤 그런 신호는 0건입니다.
- **예산안 제안 설명의 사업 목록을 항목마다 읽게 했습니다(§4의 2·3).** "주요사업비 예산 반영 내역으로는 … 오리공원 물놀이장 설치 공사비 10억 원, …" 같은 목록입니다. 최종 신호 75건 중 40건이 이 목록에서 나왔고, 20건 무작위 대조에서 목록 항목 9건은 사업명·금액·연도·약속 수준·발언자가 모두 맞았습니다. 목록 밖 11건은 사업명 온전 1건, 금액 틀림 3건으로 여전히 약합니다(§6).

## 1. 접속: HTTPS는 새 연결이 거의 다 끊기고, 회의록은 HTTP로 받음

`www.sncouncil.go.kr`은 이 환경의 허용 도메인에 들어 있습니다. 프록시는 CONNECT에 `200 Connection Established`로 답했고, 프록시 상태(`/__agentproxy/status`)의 `recentRelayFailures`도 비어 있어 **정책 차단(connect_rejected)이 아닙니다.** 끊기는 곳은 그 뒤 TLS 핸드셰이크입니다. **따로 허용할 호스트는 없습니다.**

| 호스트 · 방법 | 시도 | 결과 |
|---|---:|---|
| 의회 `https://` · curl 기본 설정 (robots.txt, 간격 3~10초) | 17 | 성공 2, 나머지 15는 ClientHello 직후 `Connection reset by peer` |
| 의회 `https://` · `openssl s_client` (프록시 경유; 기본, `-tls1_3`, `-tls1_2`, `-tls1_2 -cipher AES128-SHA`·`AES256-SHA`) | 10 | 10번 모두 ServerHello 전에 `errno=104`(reset) |
| 의회 `https://` · HWP 3개를 다시 받아 해시 대조, curl (파일당 최대 10번, 간격 12초) | 30 | 30번 모두 reset. 대조하지 못함 |
| 의회 `https://` · 같은 3개, httpx 기본 TLS·연결 재사용 (파일당 최대 10번, 간격 10초) | 30 | 30번 모두 `ConnectError`. 대조하지 못함 |
| 의회 `http://` · curl (robots.txt, 첫 화면, 목록, 상세, HWP 1개) | 7 | 7번 모두 200 |
| 의회 `http://` · 크롤러 (§3) | 88 | 88번 모두 성공, 재시도 0 |
| 성남시청 `https://` · curl 기본 설정 (robots.txt; §8에서는 받았던 곳) | 6 | 6번 모두 같은 reset |
| 성남시청 `https://` · `openssl s_client -tls1_2 -cipher AES128-SHA` | 1 | reset |
| 성남시청 `http://` · curl | 1 | `301` → `https://` (HTTP로는 받을 수 없음) |
| 성남시청 `https://` · 크롤러 (§8.3 설정 그대로, `legacy_tls_hosts`) | 11 | 첫 연결에서 `ConnectTimeout` 3번 재시도 뒤 연결, 이후 10번(35 MB 파일 포함) 모두 성공 |

- **원인은 정하지 못했습니다.** openssl은 버전·암호를 바꿔도 한 번도 ServerHello를 받지 못해, 의회 서버가 받는 TLS 버전과 암호를 확인할 수 없었습니다. 그래서 §8.1처럼 "오래된 암호만 받는 서버"라고 볼 근거가 없고, 의회 호스트에는 `legacy_tls_hosts`를 쓰지 않았습니다.
- 어제 받았던 성남시청도 오늘 curl·openssl로는 같은 모양으로 끊겼습니다. 서버 한 곳의 설정보다 **이 컨테이너에서 두 기관 서버로 가는 경로에서 새 TLS 연결이 끊기는 문제**일 가능성이 있습니다. 다만 성남시청은 크롤러가 한 번 연결한 뒤 그 연결로 나머지를 모두 받았고, 의회는 httpx로도 30번 모두 연결하지 못해, 두 곳이 똑같지는 않습니다.
- 의회는 HTTP 요청을 HTTPS로 넘기지 않고 그대로 제공합니다(첫 화면 `200`, `/kr/main.do`로 JS 이동). **그래서 회의록 34건은 HTTP(평문)로 받았습니다.** 프록시는 그대로 거쳤고, 인증서 검증을 끈 것이 아니라 TLS 없이 받은 것입니다. 크롤러 코드에 https → http 자동 전환은 넣지 않았고, 설정에서 이 호스트의 게시판 주소를 `http://`로 적은 것뿐입니다. robots.txt도 HTTP로 읽은 규칙을 따랐고, 요청 간격(1.5초)과 파일 상한(40)은 원래대로 뒀습니다.
- **전송 중 변조되지 않았다는 보장이 없습니다.** 받은 파일마다 SHA-256이 저장 주소(`raw_uri`)에 남아 있습니다(아래 표). HTTPS로 다시 받아 대조하려 했지만 60번 모두 연결하지 못했습니다. 확인한 것은 손으로 한 번, 크롤러로 한 번, HTTP로 두 번 받은 제312회 예결특위 HWP의 해시가 같다는 것뿐입니다(`58b4dcce…`). 같은 경로로 두 번 받은 것이라 변조 여부의 증거는 되지 못합니다.
- 성남시 예산서 6권은 HTTPS(크롤러)로 받았습니다. 6권 모두 바이트 수와 쪽수가 [`real-data-budget.md` §8.4](real-data-budget.md#84-권별-측정)와 같습니다(16,718,816 / 35,367,861 / 422,198 / 15,716,600 / 5,109,434 / 4,576,316바이트; 1,525 / 460 / 13 / 1,451 / 379 / 329쪽).

- **목록**: "최근회의록"(`/kr/assembly/late.do`)이 본회의·상임위·특위의 모든 회의록을 최신순으로 보여 줍니다. 한 쪽에 10행, 2026-09-28 기준 6,811건(682쪽)입니다. 열은 번호·대수·회수·차수·회의명·일자("2026.09.22 화요일")이고, 쪽 넘김은 `?pageNum=N`입니다. "회기별"·"회의별"·"연도별" 목록은 AJAX 검색 폼이라 쓰지 않았습니다.
- **회의명**: 링크 글자는 "[임시] 예산결산특별위원회"처럼 짧고, 회수·차수·날짜가 든 전체 이름은 링크의 `title` 속성에만 있습니다("제312회 예산결산특별위원회 제1차(2026.09.04.)").
- **상세**: `/record/recordView.do?key=<40~80자리 16진수>`. 회의록 전문이 HTML로 들어 있습니다(예결특위 한 번에 약 0.8 MB, 본문 약 21만 자). 같은 쪽에 **원본 HWP**(`/record/HwpDownload.do?key=…`, 같은 key)와 부록(`appendixDownload.do`, 심사자료 등)이 있습니다.
- **HWP**: HWP 5.0, 예결특위 한 번이 249,856바이트, `Content-Disposition: attachment; filename="10E0110312012.hwp"`. `Last-Modified`는 없습니다. 기존 HWP 파서(`parsing/hwp.py`)가 그대로 읽습니다. 그래서 HTML 상세를 문서로 받는 기능은 만들지 않고 HWP를 받았습니다.
- **발언자 표시**: 의원은 **"○조우현위원  질문"**(이름에 "위원"이 붙고 두 칸), 공무원은 "○교통도로국장 유동  답변"(직함, 한 칸, 이름, 두 칸), 의장·위원장은 "○위원장 서은경"입니다. 합성 데이터와 CLIK 계약 픽스처는 모두 "○위원 박지훈" 모양이라, 의원 발언을 하나도 알아보지 못했습니다(§4의 1).
- **첨부 호스트**: HWP·부록 모두 같은 호스트입니다. 인터넷방송(`cast.sncouncil.go.kr`)은 영상이라 쓰지 않았습니다.
- **robots.txt**: `User-agent: *` / `Allow:/` 두 줄입니다. 막힌 경로는 없습니다.

## 3. 설정과 실행

`manage seed`가 새 수집원 `minutes_boards`(adapter `crawler`, 기본 꺼짐)를 만듭니다. 켜 두면 매일 회의록 cron(`ingest_minutes`)이 `clik_minutes`와 함께 돕니다.

```sql
UPDATE sources SET enabled = true, config = '{
  "doc_type": "council_minutes", "max_files": 40, "max_file_mb": 20, "delay_seconds": 1.5,
  "max_pages": 40,
  "boards": [
    {"url": "http://www.sncouncil.go.kr/kr/assembly/late.do",
     "institution_code": "CN-41130", "publisher": "경기도 성남시의회",
     "detail_pattern": "recordView\\.do", "attachment_pattern": "HwpDownload\\.do",
     "id_param": "key", "page_param": "pageNum", "title_attr": true,
     "title_keywords": [], "title_pattern": "본회의|예산결산특별위원회"}

WHERE key = 'minutes_boards';
```

```bash
uv run manage sources ingest -s minutes_boards --days 393 --until 2026-09-28
```

## 4. 고친 것

테스트는 모두 실제 HTML과 회의록 줄을 줄여 만들었습니다(`tests/unit/test_crawler.py`, `test_parsing.py`, `test_llm.py`).

1. **의원 발언을 알아보지 못함.** 발언자 정규식은 "○직함 이름"만 읽었습니다. "○조우현위원  보니까 그래서…"는 직함 "조우현위원", 이름 "보니까"로 읽히거나(의원 아님), 아예 발언자 줄이 아니어서 **앞 공무원 발언의 이어지는 줄**이 됐습니다. 제312회 예결특위 한 번에서 발언 표시 1,669줄 중 의원 발언으로 읽힌 것이 0이었고, 질문·답변 묶음(exchange)도 0개였습니다. 이제 "이름+위원/의원, 두 칸"을 의원으로 읽습니다(`parsing/chunking.py`의 `GLUED_MEMBER_RE`). 뒤가 한 칸인 "○전문위원 홍길동"은 그대로 직함+이름입니다. 규칙 기반 추출기의 질문·답변 나누기(`_answer_text`)도 같은 정규식을 씁니다. 고친 뒤 같은 회의록에서 발언 1,667개 중 의원 650개, 묶음 651개가 나옵니다.
2. **예산안 제안 설명의 사업 목록.** 예산안을 내는 본회의(와 예결특위 첫날)에서 행정기획조정실장이 "주요사업비 예산 반영 내역으로는 판교 시스템반도체 연구센터 조성 263억 원, 오리공원 물놀이장 설치 공사비 10억 원, … 등을 반영하였습니다."라고 읽습니다. 예산서 행과 이름·금액이 그대로 맞는, 이 제품이 찾는 문장입니다. 그런데 규칙 기반 추출기는 청크 하나에서 신호를 하나만 내서, 이 목록은 "제출한 제1회 추가경정예산안은 국도비 보조사업" 같은 제목에 4조 1,804억 원(추경 총액) 같은 금액이 붙은 신호 하나가 되거나, 아예 신호가 되지 않았습니다. 이제 "예산 반영 내역" 머리말이 같은 줄이나 바로 앞 줄에 있고 "사업명 N억 원" 항목이 셋 이상인 **집행부 발언** 줄은, 항목마다 신호를 냅니다(금액은 항목의 금액, 연도는 같은 청크의 "2026년도 제1회 … 추가경정예산안", 약속 수준은 committed). 전출금·출연금·상환·환급금·쿠폰·지원금·융자·상품권·축하금 항목은 사업이 아니라 뺍니다. 분야 분류가 `other`인 항목도 기존 규칙대로 뺍니다. 그래서 "판교 시스템반도체 연구센터 조성", "고기교 주변 교차로 개선사업", "해님달님놀이터 조성" 같은 항목은 여전히 신호가 되지 않습니다.
3. **긴 발언을 자를 때 머리말을 다음 조각에도.** 제307회 본회의(2026년 본예산 제안)는 2,400자에서 자른 첫 조각이 정확히 "주요사업비 예산 반영 내역입니다."로 끝나고, 목록은 머리말 없이 다음 조각에 들어갔습니다. 잘린 조각의 마지막 줄이 60자 이하이면 다음 조각도 그 줄에서 시작합니다(두 조각이 한 줄 겹침).
4. **링크의 `title` 속성을 제목으로 (`title_attr`, 선택).** 켜면 글 링크의 `title="…"`을 글 제목으로 씁니다. 끄면(기본) 전과 같습니다.
5. **상한 뒤에는 상세 페이지도 열지 않음.** 전에는 `max_files`에 걸린 뒤에도 글마다 상세 페이지를 열고 나서야 파일을 건너뛰었습니다. 이 사이트는 상세 한 쪽이 약 0.8 MB라, 이제 상한에 걸리면 상세를 열지 않고 `skipped_cap`만 셉니다.
6. **`minutes_boards` 수집원**(§3).

### 7.1 실행한 순서대로는 사슬 1개

처리 순서는 회의록 → 예산서 → 조달청이었지만, 회의록은 §4의 2·3을 고친 뒤 다시 처리했습니다. 그래서 연결 순서는 **예산서 → 조달청 → 회의록**이 됐습니다. 이 순서에서 회의록 신호와 예산 신호가 한 기회에 든 것은 하나뿐이었습니다. "중원노인종합복지관 경로식당 확장공사"(2026-08-27 추경 제안 11억 ↔ 2026 본예산 70,000천원)로, 맞는 짝입니다. 조달청 신호가 든 것은 없었습니다.

**다른 짝들이 붙지 않은 까닭**: 연결기는 후보 기회를 `first_seen_at <= 신호 관측일 + 90일`로 거릅니다(`pipeline/link.py`의 `_candidates`). 예산서 신호의 관측일은 게시일이 없어 파일의 `Last-Modified`(6권 모두 2026-06-18)를 씁니다([§8.8의 4](real-data-budget.md#88-전체-실행에-필요한-것)). 그래서 2025-11-20이나 2026-03-12의 발언은, 이미 있는 "2026-06-18에 처음 본" 예산 기회를 후보로 보지 못하고 새 기회를 만들었습니다. 연결된 경로당 발언은 2026-08-27이라 이 창 안에 들었습니다.

### 7.4 읽은 것

- **실제로 나온 사슬은 "예산안 제안 설명 → 예산서 행"입니다.** 이름과 금액이 거의 그대로 맞아 사람이 봐도 같은 사업입니다. 다만 발언이 예산서보다 크게 앞서지는 않습니다. 2026년도 예산안은 2025-11-20에 제안되어 2025-12-18 제307회 본회의 제3차의 안건이 됐고, 제1회 추경은 2026-03-12에 제안되어 03-18 제309회 본회의 제2차의 안건이 됐습니다(표결 부분은 읽지 않음). 이 사슬의 값은 "몇 달 앞선 신호"보다 **예산서가 게시되기 전에, 읽기 쉬운 문장으로 주요 사업과 금액을 먼저 준다**는 데 있습니다. 예산서 게시일은 이번에도 알 수 없었습니다(`Last-Modified` 2026-06-18).
- README 첫 문단의 "입찰공고 6~18개월 전의 '내년도 본예산에 반영하겠습니다'"형 발언(시정질문·예결특위 질의 답변)은 규칙 기반 추출기로는 사업명이 조각나서(§6) 예산서 행과 이어지지 않았습니다. LLM 추출기로 같은 34건을 돌려 보는 것이 다음 순서입니다. 청크 1,518개가 선별을 통과하므로, 먼저 `make eval-llm`의 `--dry-run`처럼 비용을 추정하고 사람이 한도를 정해야 합니다.
- **연결 순서에 따라 결과가 크게 달라집니다**(1개 대 17개). 원인은 예산서 관측일이 `Last-Modified`라는 점(§7.1)입니다. 한 페이지 목록의 예산서에 회계연도로 관측일을 정하는 규칙(예: 본예산은 전년 12월)을 넣거나, 늦게 들어온 신호가 앞선 기회를 볼 수 있게 후보 창을 바꾸는 것이 다음 일입니다. 이번에는 연결 기준과 창을 바꾸지 않았습니다. 앞의 규칙은 넣어서 §8에서 쟀습니다. 예산서를 먼저 연결해도 사슬이 1개에서 17개가 됐지만, 추경과 제안일~12월 사이의 발언은 남았습니다.
- 섞임·틀림은 대부분 "건립", "노후시설 정비", "리모델링"처럼 흔한 말과 같은 분야가 겹친 경우입니다. §8.7에서 예산 행과 조달 공고 사이에 본 것과 같은 모양입니다.


## 8. 예산서 관측일을 회계연도로 묶은 뒤 (2026-09-29)

§7.1에서 연결 순서에 따라 사슬이 1개와 17개로 갈렸습니다. 원인은 예산서 6권의 관측일이 모두 `Last-Modified`(2026-06-18)라는 점이었습니다. 브랜치 `fix/budget-observed-date`의 커밋 `a2bce81`은 게시일이 없는 한 페이지 목록의 예산서에 상한을 둡니다(`sources/crawler.py`의 `adopted_by`). N년 본예산은 N-1년 12월 31일, N년 추경은 N년 12월 31일보다 늦을 수 없습니다. `Last-Modified`가 그보다 이르면 그대로 씁니다. 원래 값은 `structured.last_modified`에 남고, 상한을 쓴 권은 `structured.published_from`이 `"fiscal_year"`입니다. 이 절은 그 변경을 같은 실데이터로 main과 비교한 것입니다.

- 추출은 모두 **규칙 기반 추출기**(`APP_LLM_PROVIDER=heuristic`)입니다. 실행마다 `APP_ANTHROPIC_API_KEY`를 환경에서 빼고 돌려 Anthropic 호출은 0번입니다.
- **조달청은 넣지 않았습니다.** §7.3에서 회의록 신호가 든 기회에 조달청 신호가 하나도 붙지 않았고, 30일치에 이 사업들의 공고가 없었기 때문입니다. 그래서 이 절의 기회 번호와 묶음은 조달청을 함께 연결한 §7.2와 조금 다릅니다(§8.3).
- 새 컨테이너에 PostgreSQL 16 + `postgresql-16-pgvector`, Redis, `tesseract-ocr`·`tesseract-ocr-kor`·`fonts-nanum`을 설치했습니다(Docker 없음). 실행마다 DB와 Redis db 번호를 따로 썼습니다.

### 8.1 방법

1. **기준 DB 두 개.** `base_main`은 `origin/main`(`9b464a7`)을 따로 꺼낸 작업 트리의 코드로, `base_branch`는 이 브랜치의 코드로 만들었습니다. 각각 `manage db upgrade` → `manage seed --anchor 2026-09-25` → [`real-data-budget.md` §8.3](real-data-budget.md#83-설정과-실행)과 §3의 설정 그대로 `budget_boards`·`minutes_boards`를 켬 → `sources ingest -s budget_boards --days 400 --until 2026-09-27` → `sources ingest -s minutes_boards --days 393 --until 2026-09-28` 순서입니다.
2. **실행 네 번.** 기준 DB를 `createdb -T`로 복사하고, 맞는 코드로 돌렸습니다.
   - **A (한 번에)**: 모든 문서가 대기 중인 상태에서 `manage pipeline run` 한 번. 연결기는 신호를 관측일 순서로 처리하므로 §7.2(관측일 순서로 다시 연결)와 같은 순서입니다.
   - **B (예산서 먼저)**: SQL로 회의록 34건의 `parse_status`를 `'skipped'`로 바꾸고 `manage pipeline run`, 다시 `'pending'`으로 되돌리고 `manage pipeline run`. §7.1에서 사슬이 1개였던 순서를 이렇게 만들었습니다.
3. 실행마다 회의록 신호와 예산서 신호가 함께 든 기회를 세고, 하나씩 §7.2의 표와 사업명으로 맞춰 판단했습니다(제 판단).

  - **오리공원 물놀이장**: main B에서는 혼자 남았는데, 브랜치 B에서는 **틀린 짝**이 됐습니다. 2026 본예산이 2025-12-31로 당겨지면서, 금액이 같은(10억) "공동구 광센서 자동화재탐지설비 설치 공사" 기회가 후보 창에 들어왔기 때문입니다. 추경의 "오리공원 물놀이장 설치공사" 행은 혼자 기회 하나를 이루고 있습니다.
  - **수내역 광장**: 브랜치 B에서 추경의 "수내역 광장 재정비공사" 행과 같은 기회에 들었지만, 그 행이 예산서 연결 단계에서 2026 본예산 "보도 정비공사" 기회(2025-12-31)에 먼저 붙어 있었던 덕입니다. 섞임입니다.
- **상한이 제안일보다 늦습니다.** 2026 본예산의 상한 2025-12-31은 2025-09의 제305회 발언(2025년 제3회 추경 제안)에서 90일이 넘습니다. 그래서 "성남제일초등학교 본관동 개축"(09-12 발언 → 2026 본예산 2,000,000)은 브랜치 B에서 빠졌습니다. 2026년도 예산안은 2025-12-18 제307회 본회의 제3차의 안건이었으므로(§7.4) 이 해의 상한은 실제와 2주쯤 차이입니다. 상한을 더 당길 근거는 이 자료만으로는 약합니다.
- **새 틀림·섞임이 생깁니다.** 관측일이 앞당겨진 만큼 발언의 후보가 늘어, 이름보다 금액·분야가 맞는 다른 사업에 붙는 경우가 생겼습니다(오리공원, 수내역, 여수동의 브랜치 A). 연결 기준(`score_candidate`, 금액이 같을 때의 가산점)은 이번에도 바꾸지 않았습니다.
- 정리하면, **이 변경은 연결 순서에 따른 차이(1 대 17)를 없애는 데는 도움이 됩니다**(브랜치 17·18). 맞음의 수는 A에서 8 → 10, B에서 1 → 9입니다. 추경 쪽과 제안일~12월 사이의 발언은 남은 문제입니다. 늦게 들어온 신호가 앞선 기회를 볼 수 있게 후보 창을 바꾸는 방안(§7.4)은 여전히 따로 볼 일입니다.

### 8.7 접속

- 성남시의회는 §1·§3대로 `http://` 게시판 주소로 받았습니다. 두 번 모두 요청 88번, 재시도·오류 0입니다. 이번에는 HTTPS를 따로 시도하지 않았습니다. 받은 34건의 SHA-256이 §1의 목록과 같지만, 같은 경로(HTTP)로 받은 것이라 변조가 없었다는 증거는 되지 못합니다(§1의 주의 그대로).
- 성남시청(`https://`, `legacy_tls_hosts`)은 두 번 모두 받았습니다. main 쪽은 요청 10번에 재시도 0, 브랜치 쪽은 첫 연결에서 `ConnectTimeout` 3번 재시도한 뒤 연결되어 요청 13번이었습니다. 회로 차단기는 열리지 않았습니다. 강남구는 §8.3과 같이 첨부 2개를 robots.txt로 건너뛰었습니다.
